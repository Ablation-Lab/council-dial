# Council Dial

## What it is

Council Dial is a Claude Code plugin that has a small panel of Claude reviewers check your code, docs or plan. In its standard setup, three reviewers each check the work on their own, a judge checks every finding they report and throws out the ones that don't hold up, and an appeal agent rechecks anything the judge threw out. You make the final call on what to keep.

It's for people who already review work with Claude Code and want to know which way of reviewing works best for their kind of work: for example, whether specialised reviewers find more than generalists, or whether a debate round is worth the extra tokens. Every run's setup and what it found go into a log in your project, so over time you can compare setups on your own material.

It's a research tool. It doesn't claim that any setup, including the judge and the appeal, works better than another; the log is there so you can measure that on your own work.

## Quick start

1. In Claude Code, run `/plugin install council-dial --marketplace Ablation-Lab/council-dial` (details and older versions under [Install](#install)). It needs Node.js 18 or later.
2. In your project, say `Run a standard review council on the diff of this branch`. Claude says how many subagents it will start. Once you have logged runs of that type, it also gives a rough token estimate from them; until then it has none, and suggests a smaller trial run first. Either way, it waits for your yes.
3. Read the findings, most serious first. If the appeal thinks the judge wrongly threw something out, Claude shows you both views and you decide.
4. After a few runs, ask `How do the council types compare in my review log?`

To try it first on a small made-up module with known answers, see [Try it with the sample](#try-it-with-the-sample-for-reviewers).

## Overview

When you want code, docs or a plan reviewed, Council Dial has Claude run a review council of subagents set up the way you choose: specialised or generalist reviewers, a judge (with an appeal of the findings it throws out), a pooled list or a majority consensus to combine their findings, and optional debate, sequential and single-reviewer baseline runs. Claude tells you how many subagents a run will use and, from your earlier runs of the same type, roughly how many tokens, and waits for your yes. Each run's type and results go into a log in your project, so you can compare council types over time.

It was made for research on review councils, where the question isn't only "what did the review find?" but "which kind of review finds the most for the effort?". It adds one skill, `council-dial` (in Claude Code: `/council-dial:council-dial`), and one read-only agent, `council-dial:council-reader`, which the council's agents run as unless you allow running code. It's an independent project, not made or endorsed by Anthropic.

## Two editions

Council Dial comes in two editions:

- **Council Dial** (this plugin, from this repository) is for research runs. A local script fills in the briefs, refuses counts that don't add up before they're logged, keeps the review log and works out the comparison table. It needs Claude Code and Node.js.
- **Council Dial Lite** is the script-free edition, for places where a script can't run or isn't accepted. Anthropic's plugin directory asked for changes to the full edition because of its script, and Lite is the edition made for the directory; this edition stays available from this repository's marketplace either way. In Lite, Claude does every step with its own tools, from the same brief templates. By default its agents only read, with the same read-only tools as the full edition's; Claude saves each report itself, and a fresh agent checks the summary against the reports. An opt-in raw mode saves every brief and report and leaves the summary and the counts to a fresh agent, perhaps on a stronger model. It has its own repository, [Ablation-Lab/council-dial-lite](https://github.com/Ablation-Lab/council-dial-lite), which holds only Markdown, JSON, its licence, its icon and two git settings files.

The trade-off: Lite needs no Node.js, but nothing checks its log mechanically. Claude checks the counts, and works out estimates and the comparison table, by hand, so they can contain mistakes, and Lite can't read the session's effort level. Lite runs are logged on their own, in `reviews/lite/`, marked `"edition": "council-dial-lite"`, with labels starting `lite:` and run ids starting `lite-`, so they never mix with research runs. Use Council Dial for runs you'll report as research.

## How it works

1. **Dial in the type.** Say what to review and how, for example "run a specialised council with a judge and a debate round on this branch". If you don't say how, Claude suggests Standard (three specialised reviewers, a judge and an appeal), Quick (three generalists, pooled) or Thorough (Standard plus debate and a baseline). Either way it tells you how many subagents the run uses and, once you've logged runs of that type, a rough token estimate (see [Models, tokens and time](#models-tokens-and-time)), and waits for your yes before it starts.
2. **Plan.** A local script turns your choices into the exact briefs for each reviewer, the debate round, the judge and the appeal, and logs the run's type straight away. Claude doesn't open the material before then: it only lists the files to check they exist, so the target line comes from your words, not from its own reading. Anything you want left out, such as a folder of sample data, goes in the one-line description of the target, because that line is what every brief gets.
3. **Run.** Claude starts the subagents step by step: reviewers in parallel (or one at a time, each seeing the earlier reports), then the debate round, then the judge, or Claude merges the reports itself for pooled and consensus. The baseline reviewer works alone and never sees the council's reports. Then an appeal agent checks the findings the judge threw out and, in brief version 3, every severity the judge changed and every finding it left at LOW, seeing only those findings and the judge's reasons. In version 2 it runs only if the judge threw something out.
4. **Report.** You get the council's findings, most serious first, with fixes, and, for a judged council, every finding whose severity the judge set differently from a reviewer's, up or down (including where reviewers disagreed and the judge took one of their ratings), with each reviewer's severity and the judge's reason where it gave one; and what the baseline found that the council didn't (and the reverse). Each finding the appeal thinks was wrongly thrown out (and, in version 3, each severity it thinks is too low or too high) is listed with the judge's view and the appeal's, and you make the call.
5. **Log.** Claude records the counts: findings per reviewer, after combining, confirmed, partly real, overstated, understated and dismissed, by severity, the baseline's, each appealed finding and your call on it, and the time taken. It also records the main session's model, the model each subagent was asked to use, and the tokens (each agent's context size when it finished, not a billed total), tool uses and time Claude Code reported for each subagent (see [Models, tokens and time](#models-tokens-and-time)), and saves every agent's full report in a folder named by the run id, so you can see exactly what each found and what the judge threw out and why. Ask for a run's setup and Claude gives its type, roles, brief version, models, the session's effort level and Council Dial version, and the command that reruns it. After fixes are rechecked, it adds how many fixes failed the recheck and how many caused new problems.
6. **Compare.** Ask "how do the council types compare?" and Claude shows a table by type: findings per run, the share kept (REAL or OVERSTATED) and dismissed, how often the judge cut a kept finding's severity, minutes per run (wall time and critical path, kept apart), tokens per run (and the appeal agent's tokens), fixes that failed recheck, regressions, council against baseline, and how many dismissals the appeal flagged and you reinstated (and, in version 3, how often it disagreed with the judge's severities).

The types:

| Dial | Choices |
|---|---|
| Reviewers | **specialised** (each covers one area: by default correctness, security and privacy, docs and policy accuracy; or areas you name) or **generalist** (all review everything; 1 to 9 of them) |
| Combine | **judged** (a fresh judge merges duplicates and checks each finding), **pooled** (every finding, duplicates merged, nothing verified) or **consensus** (only findings a majority of the reviewers raised, such as 2 of 3 or 3 of 4; the rest listed as minority findings) |
| Appeal | on by default for **judged** councils: one fresh agent sees only the findings the judge marked NOT REAL, with the judge's reasons, and in brief version 3 also the severities the judge changed and the findings it left at LOW (never the reviewers' reports or how the target was described), and flags any finding it thinks was wrongly thrown out or wrongly rated. It doesn't overrule the judge; you decide. Say "without the appeal" to turn it off. The type's name ends in `+appeal`, so runs with and without it are compared separately |
| Extras | **debate** (one round where each reviewer answers the others' findings), **sequential** (reviewers go one at a time and look for what the earlier ones missed), **baseline** (one extra reviewer alone, for comparison) |
| Model | by default the subagents use your session's model; or name one, Sonnet, Opus, Haiku or Fable, for all of them, or one per seat (each reviewer, the judge, the appeal and the baseline), such as Sonnet reviewers, a Haiku judge and an Opus appeal. The type's name ends in `@` and that model (such as `@sonnet` or `@claude-opus-5-5`), or, when seats differ, each seat's (such as `@{reviewers=sonnet, judge=haiku, appeal=opus}`), so models are compared separately |
| Effort | left to the default unless you name a level (low, medium, high, xhigh or max) for all the seats or for one seat. A level you set goes in the type's name after its seat's model, such as `@sonnet/high` or `appeal=opus/max`, so runs at different effort levels are compared separately |

## Version 2 vs version 3

Council Dial 1.5.0 and later write brief version 3 unless you ask for version 2 (say so, and Claude plans with `--brief-version 2`). Version 2 is the wording of every run before 1.5.0, kept byte for byte so those runs stay comparable. Version 3 came from three stress-test runs of the appeal (on Opus, Sonnet and Haiku), which showed the judge could never raise a severity, and a judge running a "scratch" check although running code wasn't allowed. Every difference:

| | Version 2 | Version 3 |
|---|---|---|
| The judge's rulings | REAL, OVERSTATED (with the right severity) or NOT REAL. It can keep or cut a reviewer's severity, but has no ruling to raise one, so a finding never ended above its highest reviewer's rating: one finding, silent data loss, ended LOW, MED or HIGH depending only on whether one reviewer happened to rate it high. | Five rulings, each comparing the judge's own severity with the highest a reviewer gave: REAL (the claim holds, same severity), PARTLY REAL (part of the claim doesn't hold, same severity), OVERSTATED (lower), UNDERSTATED (higher, so a severity can be raised) and NOT REAL. For every OVERSTATED and UNDERSTATED finding, the judge gives each reviewer's severity, its own, and a one-line reason. |
| How the judge sets severity | Not stated; when reviewers disagreed, judges took the higher rating. | From the evidence, "not from how many reviewers raised it or how they rated it". |
| Numbering | Left to the judge (one used M1, M2; another used letters). | M1, M2 and so on, with the reports each came from and the severity each gave, so citations and the appeal's items are reliable. |
| The final ranked list and the counts | REAL and OVERSTATED findings; the log counts confirmed, overstated and dismissed. | Every finding that isn't NOT REAL, with its number and ruling; the log also counts `partlyReal` and `understated`, and the five add up to the merged count. |
| The appeal | Checks only the judge's dismissals, and runs only if there were any. | Also checks every severity the judge changed (up or down) and every other finding it kept at LOW: SEVERITY FAIR, TOO LOW, TOO HIGH or UNSURE. It runs if there's a dismissal or a severity to check, so in nearly every judged council. Every verdict is logged, fair ones included, and how often it disagrees on unchanged LOW findings is reported separately, so you can judge whether that part earns its cost. It still never sees which model or effort produced a finding. |
| The running-code rule | "Don't run code from the material unless your brief says the user allowed it": silent on checks of the agent's own, and a judge ran a scratch Python check it read as allowed. | "Run nothing unless the user allowed running code": no code from the material, no scripts or one-off checks of its own (even in a scratch folder), no tests and no shell commands. If you allow running code, all of those are allowed. |
| How that rule is enforced | Only by the brief's wording. | By a tool limit: every agent is the plugin's read-only agent, `council-dial:council-reader`, with only the Read, Grep and Glob tools, so it can't run or write anything whatever the material says. If you allow running code, Claude plans with `--allow-running-code` and the agents are general-purpose. |
| The agent's system prompt | The general-purpose agent's built-in system prompt, with every tool your session allows. | The read-only agent's own definition is its system prompt, in place of the general-purpose one: two short sentences telling it to do what the message asks, and that it can read and search files but can't run commands or programs or change any file. |
| The type's name | Such as `specialised-3/judged+appeal @sonnet`. | The same with ` v3` before the models, such as `specialised-3/judged+appeal v3 @sonnet`. |

**Both versions, from 1.5.0:** the effort settings check isn't a brief difference. For a seat with no effort set, on another model than the session's, `plan` reads the level saved for that model in your settings files (the user file only with `--read-effort-settings`) and shows it in the seat summary, whichever version the run uses. It changes what you're shown, not what the agents are told.

**Both versions, from 1.5.2:** Claude doesn't read the material before `plan` writes the briefs; the appeal's severity block has a fixed layout, with one label per field; a reviewer the judge credits only for a side remark, with no severity of its own, doesn't count as giving that finding a severity; only words that explain a severity count as the judge's reason; and the appeal's counts are taken from the verdicts it lists, not its own count line. None of these changes a brief template, so they don't change which runs compare together.

**Why runs of the two versions must be compared separately:** version 3 changes what the judge may rule and how findings are counted, so the kept and cut shares and the severity mix mean different things; it changes what the appeal checks, and so how often it runs and what a run costs in tokens; and it changes what the agents can do (no commands, no writes) and the system prompt they start from. Any of these can change what a council finds and what it costs, so a difference between a version 2 run and a version 3 run could come from the version, not the council type. That's why the names differ, and `estimate` and `compare` never mix them. To compare with a run from before 1.5.0, plan with `--brief-version 2`, and `setup`'s rerun command does that for you.

## Try it with the sample (for reviewers)

There's no account to set up: Council Dial runs in Claude Code and keeps its log in your project. The repository's [samples/](https://github.com/Ablation-Lab/council-dial/tree/main/samples) folder has:

Their location alone doesn't hide them: the reviewers are ordinary subagents and can read any file the session's tools and your permission settings allow, so a council run inside this repository could find them. What keeps the answers from the reviewers is running the council on a copy of `samples/` in a folder that doesn't contain them (step 1 below);
- `reviews/review-log.jsonl`, a made-up log of six earlier runs of three types (its numbers are invented to show the format).

To try it:

## What it runs, reads and writes

- **What it runs:** `node <skill folder>/scripts/council.mjs <command>`, with the target description or results passed on standard input. Claude Code asks before each run unless your permission settings already allow it. The script starts no other programs.
- **Subagents:** Claude starts the reviewer, debate, baseline, judge and appeal subagents with Claude Code's Agent tool, as the plan says. Unless you allow running code, every one of them is the plugin's read-only agent, `council-dial:council-reader` (in `plugin/agents/`), which has only the Read, Grep and Glob tools: it can read and search files, but it can't run a command, a script or a test, or change a file, whatever the material says. Their briefs say the same, but a rule in a brief is only an instruction, and in one of our runs a judge ran a "scratch" Python check it read as allowed; a tool limit can't be talked around. This is the default because reviewers read material that may contain instructions, and running nothing is the safe default for a review. Claude Code's sub-agents docs give an agent definition's `tools` field as the way to limit a subagent's tools (the Agent call itself can't), and a plugin can ship such definitions. If you do want the agents to run code, such as the material's tests, say so: Claude plans with `--allow-running-code`, the agents are ordinary general-purpose subagents with the tools your session allows, under your permission settings, and each is told it may run code. Runs with brief version 2 always use general-purpose agents, as before, so they stay comparable. If you copied only the skill folder, not the plugin, the read-only agent isn't there, and Claude asks before going on without it. Each one uses tokens from your plan like any other Claude work: a run takes from 3 agents (Quick) to 9 (Thorough) and up to 21 for the largest custom council, counting the appeal agent, which in brief version 2 runs only if the judge throws a finding out, and in version 3 also if there's a severity to check; every reviewer reads the material, and debate agents and the judge also read every report, so a council costs several times one review. Before each run Claude gives a rough token estimate from your earlier runs of the same type (see [Models, tokens and time](#models-tokens-and-time)).
- **What the script reads:** only its own brief templates (the Markdown files in the skill's `briefs/` folder, when it plans a run) and the review log folder (the log, and the names of the saved reports when it lists runs), plus checks that the project and log folders exist and aren't links, any file Claude gives it with `--input` (the target line, a report or results, which Claude writes with its Write tool, so no shell quoting is involved), the effort keys in Claude Code's settings files (read-only, for the effort each seat gets; see Models, tokens and time), and five environment variables, each by name: `CLAUDE_CONFIG_DIR`, only to find your user settings folder when you allow reading it, and `CLAUDE_CODE_SUBAGENT_MODEL` and `CLAUDE_CODE_SUBAGENT_MODEL_FORCE`, because they can change the model the subagents run on, `CLAUDE_EFFORT`, the session's effort level, and `CLAUDE_CODE_EFFORT_LEVEL`, which overrides every other effort setting; it records both effort variables. It never reads the material under review.
- **What the script writes:** only the review log, in `reviews/` in your project (or a folder inside the project you choose): `review-log.jsonl`, an append-only record of each run's type, target description, counts and recheck results, `review-log.md`, a readable summary rebuilt from it after every write, and each run's saved reports, one Markdown file per agent in a folder named by the run id (`reviews/20261107-2f23/judge.md`, for example); `review-log.md` and each report are first written to a short-lived `.tmp` file next to it, then renamed into place (or deleted, if that fails). It won't write outside the project, even through a link, and won't write to a log folder, log file, run folder or report that is itself a link or has other hard links. A link inside the project that leads to another folder inside the project is followed. The token estimate (`estimate`) writes nothing.
- **What Claude reads and writes itself:** before `plan`, Claude only lists the material's files to confirm they exist; it doesn't open them until the briefs are written. The input files it gives the script with `--input` (the target line, each report, the results) go in its scratchpad or another temporary folder, outside your project.
- **Network:** the script makes none. The subagents are Claude, so the material they review reaches Anthropic the way anything in your conversation does.

## Models, tokens and time

What the log records, and what Claude Code doesn't make available:

- **Main session's model:** recorded as the model id Claude gives the script with `--main-model` (Claude reads it from its own instructions; Claude Code sets no environment variable for it, though it does give the id to a status-line script in its JSON input and sometimes to `SessionStart` hooks). Only an id shaped like a Claude model id (`claude-…`, optionally ending in `[1m]`, the suffix an older model such as `claude-opus-4-6[1m]` takes for its 1M-context window; Claude 5 models have that window without it) is accepted, and only such an id, or an alias, is read back from the log; anything else is refused when planning and dropped when reading, so a value planted in a log can't reach a type's name or the rerun command.
- **Subagents' model:** recorded as asked for, seat by seat. Claude passes each seat's model as the Agent tool's `model` on its call (the tool takes only the aliases `sonnet`, `opus`, `haiku` and `fable`), or passes none, and that seat inherits the session's model. Before the run, the plan lists every seat's model and effort, marked explicit (with the option that set it) or default; the log records them, and the type's name gives one model for the whole council (`@sonnet`) only when every seat has the same one. The judge and the appeal are never told which model or effort any seat used: Claude passes them only as the Agent tool's parameters, never in a prompt, and every agent is told the review log folder isn't part of the material. The script also records `CLAUDE_CODE_SUBAGENT_MODEL` (a default below your choice) and warns when `CLAUDE_CODE_SUBAGENT_MODEL_FORCE` overrides it. **Not available:** the model a subagent actually ran on. Claude Code shows it in `/tasks`, but doesn't report it to the main session, so the log can't confirm it, and an alias isn't resolved to a version.
- **Effort:** set only if you ask, for every seat or for one seat; Claude passes it as the Agent tool's `effort` parameter, which Claude Code's sub-agents documentation gives as the way to set effort for one call (Claude Code 2.1.292 or later; the other way is an `effort` field in an agent definition, which Council Dial doesn't use). A level the seat's model doesn't support runs at the highest level it supports below that, and an effort cap (`maxEffortLevel`) still applies. A level you set is part of the type's name; a seat with none set isn't marked, so runs with no effort set compare with runs from before 1.4.0. The log also records the session's effort level, read from the `CLAUDE_EFFORT` environment variable when Claude plans the run, and shown by `setup`. Two variable names are easy to confuse: to set the level, use `CLAUDE_CODE_EFFORT_LEVEL` (or `/effort`); Claude Code then shows the current level in `CLAUDE_EFFORT`, which is the one Council Dial reads. What we measured on Claude Code 2.1.319 with no effort set for any seat, each result checked three ways (the subagent's own echo of `CLAUDE_EFFORT`, a `SubagentStop` hook logging `effort.level`, and the subagent's transcript):
  - Seats on the session's model (no `--model`, or `--model` naming the same model) ran at the session's effort level.
  - Seats on another model ran at that model's default, not at the session's level. The models measured were Sonnet 5.5, Haiku 5.5 and Fable 5.1, on Claude Code 2.1.319: a Sonnet 5.5 seat ran at `medium`, a Haiku 5.5 seat at `medium` and a Fable 5.1 seat at `high`, each the default Claude Code's model documentation gives for that model, with no level saved for any of them. The aliases `sonnet`, `haiku` and `fable` may later point at newer models with other defaults, so these levels hold for those versions only. The sub-agents documentation says only that the session's level doesn't apply on another model, so changing the model can change effort too, which matters when you compare models; set effort explicitly to be sure.
  - Setting effort explicitly, with the Agent tool's `effort` parameter, always took effect, with `CLAUDE_CODE_EFFORT_LEVEL` not set. Council Dial now passes it for any seat you set a level for.
  - **Not available:** the level a seat actually ran at. Hooks report it (`effort.level`), OpenTelemetry carries it (the `effort` attribute), and `/tasks` shows it only when a level was set for that subagent; the completion notice Council Dial reads doesn't carry it. So the log records the session's level when the run was planned, not a confirmed level for each seat.
  - **If `CLAUDE_CODE_EFFORT_LEVEL` is set, it overrides every other effort setting:** `/effort`, `--effort`, the `effortLevel` and `modelSettings` settings, the `effort` field in an agent definition (per-seat effort) and the Agent tool's per-call `effort` parameter. So no per-seat effort choice applies, and every agent runs at that level; only an effort cap (`maxEffortLevel`) still applies. It can be set in your shell or in the `env` block of any settings file (user, project, local or managed), and a settings file's value wins over the shell's. Setting it to `auto` or `unset` doesn't clear it: Claude Code then sends no effort level, so every agent gets the API's default for its model. `plan` warns when it's set and records its value in the log, and `setup` shows it.
    - **To check it:** in the shell you start Claude Code from, run `$env:CLAUDE_CODE_EFFORT_LEVEL` in PowerShell or `echo $CLAUDE_CODE_EFFORT_LEVEL` in bash; if nothing is printed, it isn't set there. That shows only the shell's value, so also look for `CLAUDE_CODE_EFFORT_LEVEL` in the `env` blocks of `~/.claude/settings.json`, `.claude/settings.json` and `.claude/settings.local.json` (and ask your admin about managed settings). Council Dial's warning covers both, because Claude Code passes a settings file's value to the script too.
    - **To clear it for a session:** start Claude Code from a shell where it isn't set. In PowerShell, run `Remove-Item Env:CLAUDE_CODE_EFFORT_LEVEL`, then `claude`; in bash, run `unset CLAUDE_CODE_EFFORT_LEVEL`, then `claude`. That lasts only for that shell. If a settings file sets it, remove it from the file and start Claude Code again: a running session keeps a variable removed from a settings file until you relaunch.
    - **Saved levels:** a seat with no effort set, on another model than the session's, runs at the level saved for that model in your settings (`modelSettings`, which `/effort` writes), or a top-level `effortLevel` that applies to it, and only otherwise at the model's default. We confirmed this in scratch projects: with `low` saved for Haiku, a Haiku subagent given no effort ran at `low`, and at `medium`, Haiku's default, without it. So `plan` reads the effort keys, and only those, from your managed settings files, the project's `.claude/settings.local.json` and `.claude/settings.json`, and, only if you ask for `--read-effort-settings`, your user settings (`~/.claude/settings.json`, or `CLAUDE_CONFIG_DIR`), and shows each seat's level and where it comes from. It reads them read-only, keeps nothing else from them, and logs only each seat's level and source. Without `--read-effort-settings`, the plan says plainly that user settings weren't checked and that a level saved there may apply. It can't see MDM, registry or server-managed policies, or files passed with `--settings`.
    - **Per seat:** `log` records each seat's effort: the level asked for it, or `not overridden (session: <level>)`; when `CLAUDE_CODE_EFFORT_LEVEL` was set, it names that instead, and the plan warns which seats' levels won't apply.
  - **To see what each subagent ran at:** `/tasks` names each subagent's model, and adds the effort level set for that subagent, if one was (Claude Code 2.1.242 or later). It shows no level for a subagent that had none set.
- **Tokens, tool uses and time per subagent:** recorded from what Claude Code reports when each background subagent finishes (its tokens, tool uses and duration), including the appeal agent. **The token figure is a logged context size, not a billed total.** Claude Code's monitoring docs define a finished subagent's `total_tokens` as the footprint of its final API request (its input, cache creation, cache read and output tokens), "roughly the subagent's context size at completion. Not a sum across the run". The completion notice's figure isn't documented, but in one of our stress-test runs four of five agents' figures equalled the final request's total in their transcripts exactly, and the fifth was 37 tokens off; that run's judge logged 78,934 tokens against about 291,000 summed across its five requests. So the log's token totals, estimates and comparisons show how much each agent had in context, well below what was processed and billed. Each duration is wall-clock time from the agent's start to its finish: in Claude Code's Manual mode it includes any time the agent waited for you to approve a permission prompt, so it, and the critical path worked out from it, isn't pure model time. In one Manual-mode run, about 13 of a judge's 16 minutes were spent waiting on two PowerShell commands, most likely for your approval. `review-log.md` says this under its table of types. **Not available:** the split into input, output and cached tokens, and cost. That completion notice isn't a documented format and can change; if a figure isn't reported, it's logged as missing, never estimated. For exact token and cost figures per subagent, use Claude Code's OpenTelemetry metrics, filtered to subagent requests (`query_source` is `subagent`).
- **Estimate before a run:** before it plans a run, Claude asks the script for a rough estimate: the average token total (the sum of the agents' context sizes) of your logged runs of exactly that type (the same reviewers, combine, extras and model) where every agent's tokens were reported, with how many runs it's based on and their range. Bigger material costs more, because every reviewer reads all of it (and debate agents and the judge read every report too), so a run on more or larger files than those runs reviewed uses more. If there's no history for the type, or the material looks large, Claude suggests a smaller trial run first, such as a Quick council or the same council on one part of the material. The estimate is in tokens only; Council Dial gives no prices. For what tokens cost on your plan or the API, see Anthropic's pricing page, https://claude.com/pricing.
- **Comparing:** tokens per run count only runs where every agent the run had is listed with its reported tokens; a run whose list leaves an agent out, or has a gap, shows how many of its agents have figures, and one whose list has more agents than the run had says so; neither is averaged in or used for estimates. Minutes come in two measures that are kept apart, each averaged only over the runs that have it: **wall time**, from Claude's start time to when the last agent finished (for pooled and consensus, before Claude's own merge), which Claude gives; and the **critical path** (the slowest reviewer, or all of them in turn for sequential councils, then each later step), which the script works out from the agents' reported durations when every agent has one, and which leaves out Claude's own time between steps. Minutes logged before Council Dial 1.3.0 could be either, so they're shown as unlabelled; logging the run again labels them.

## Choosing models per seat

You can set a model for each seat, such as the appeal (see [Models, tokens and time](#models-tokens-and-time)). One early finding bears on that choice. It comes from a single batch, so treat it as a lead, not a guarantee.

In a direct test of the appeal, brief version 3's appeal (the same in both editions) was given ready-made judge decisions that mixed wrongful and fair dismissals and severity changes, on test material Claude wrote: 72 trials, on Opus, Sonnet and Haiku 5.5 at medium and low effort.

- **Dismissals:** every model caught nearly every wrongful dismissal: 161 of 162 in all, and at least 26 of 27 for each model at each effort level. So a Haiku appeal looked enough for checking dismissals.
- **Severity:** wrongful severity changes, nearly all one-step cuts, were caught less often: Opus 37 of 42 (about 88%), Haiku 32 of 42 (about 76%) and Sonnet 25 of 42 (about 60%: 16 of 21 at medium effort, but 9 of 21, 43%, at low).
- **Caveats:** there were three trials for each model, effort and set. Claude wrote the material, the judge decisions, the answer key and the scoring, and every appeal was a Claude model. Each wrong judge decision could be refuted by reading the material, so the batch says nothing about cases where it can't. Half of the severity misses (16 of 32) were on one item, a MED finding cut to LOW, so the ranking between models leans on it.

The batch is written up in the research repository, [evolving-review-councils](https://github.com/Ablation-Lab/evolving-review-councils/blob/main/core-method/experiment-plan.md#appeal-stress-test-first-runs-8-nov-2026), under "Appeal stress test: first runs (8 Nov 2026)". For example, add `with the appeal on Haiku` to a council prompt (Claude plans with `--seat-model 'appeal=haiku'`) for a cheaper appeal when dismissals are what you care about, or `with the appeal on Opus` when severities matter.

## Where it works

- **Claude Code**, with Node.js 18 or later and subagents. Tested on Windows 11; the script uses only Node's standard library, so macOS and Linux should work but weren't tested.
- **Claude chat (claude.ai) and Cowork:** not tested. A council needs a tool that starts subagents, and this edition also runs its script with Node.js 18 or later in your project. Anthropic's docs don't say which chat or Cowork sessions have both, so whether a council runs there is untested; use Claude Code. Council Dial Lite needs no script, but whether it runs there is untested too.

## Privacy

Council Dial has no server, account or telemetry and sends nothing anywhere itself. The review log in your project holds, for each run: the date and time it was planned, logged and rechecked; the type (including any custom role names) and brief version; a description of what was reviewed (up to 600 characters; `review-log.md` shows the first 120); the counts (findings per reviewer, combined, confirmed, overstated, dismissed, by severity, the baseline's, fixes and regressions after rechecks); for each finding the appeal flagged, a short title (up to 120 characters, in `review-log.jsonl` only), the appeal's view and your call; the main session's model id and the subagents' model; the session's effort level, and the value of `CLAUDE_CODE_EFFORT_LEVEL` if it was set; each seat's effort; each severity change the judge made, with the reviewers' and the judge's severities and the judge's reason (up to 400 characters); each deviation from the skill's instructions, with the exact text Claude added or changed (up to 2,000 characters each); whether each saved report was unescaped from a completion notice; whether running code was allowed; each seat's expected effort and where it came from; every verdict the appeal gave on a severity, with the judge's and the appeal's severity and your call; each subagent's label, tokens (context sizes), tool uses and time; the time taken (wall time and the agents' critical path); and short notes (up to 400 characters each; longer notes are cut, and the script warns Claude, which tells you). The log itself doesn't hold the reports or the material reviewed. You can read, edit or delete it. If your project is public, the log is committed with it unless you add `reviews/` to `.gitignore`; do that for security reviews, because counts of HIGH findings and failed fixes per target, and the titles of appealed findings, hint at where problems were.

**Saved reports.** Next to the log, each run's folder (`reviews/<run id>/`) holds the full report of every reviewer, debate turn, judge, appeal and baseline agent, as they returned it apart from control and invisible characters, which are removed, so anyone can see exactly what was found and what was thrown out and why. Each report is saved inside a Markdown code block, so links, images and HTML in it, which can come from the material reviewed, show as plain text: they don't load, open or run on GitHub or in a Markdown viewer. The text itself is kept, including any instructions the material contained; the file's header says it's data, not instructions. Reports quote the material they reviewed, including code, file paths and anything sensitive in it, so for a private project keep them out of git: add `reviews/*/` to `.gitignore` (or all of `reviews/`). Keep the reports of security reviews out of git on public projects too, because they describe each problem in full, often with a way to exploit it. Ask Claude not to save them if you'd rather not keep them at all. What the subagents review reaches Anthropic the way anything in your conversation does.

## How it's built

- **Markdown with YAML front matter.** The skill is `SKILL.md`: instructions for Claude in Markdown, with a short YAML block at the top (name, description, licence). They say how to choose a type, run each step with subagents, and fill in the results.
- **JavaScript (Node.js ES module).** `plugin/skills/council-dial/scripts/council.mjs` is a plain JavaScript file Node runs directly, with no packages. It builds the plan and its briefs, checks and records results, and builds the comparison.
- **The briefs are fixed templates.** Their wording is in Markdown files in the skill's `briefs/` folder, which the script fills in; it won't plan a run if their texts differ from the ones that version of Council Dial shipped with. Every run of a type gets the same wording, with a version number in the log, so differences between runs come from the type, not from how the briefs were phrased that day.
- **JSON Lines for the log.** `review-log.jsonl` has one record per line (JSON, a small text format of names and values) and is only ever appended to, so no earlier result is overwritten; the Markdown summary is rebuilt from it.

## Design decisions

- **The type is logged before the run.** A run that fails halfway still shows up (the comparison counts planned runs that were never logged), so the log doesn't quietly favour the types that finished.
- **Same briefs every time.** Comparisons mean something only if the reviewers were asked the same way.
- **A baseline is optional but cheap.** One extra reviewer working alone is the simplest test of whether a council is worth its cost.
- **Reviewers aren't told what to expect.** The description of what's reviewed goes into every brief, so the script refuses one that says the material has planted, deliberate or known problems; a sample run would otherwise look better than it is.
- **An appeal, not a second judge.** A judge can throw out a real finding, as one did in our first real run on the sample (it dismissed the planted path problem as the caller's concern). The appeal agent sees only the dismissed findings and the judge's reasons, so it reads them without the framing the judge had, and it only flags; you make the call, and the log keeps each call, so you can see whether appeals are worth their agent.
- **Severity counts add up one way.** Every combined finding is counted once by severity, a NOT REAL one at the highest severity a reviewer gave it, so the severity counts always add up to the combined total.
- **The judge can raise a severity, and the appeal checks severities (brief version 3).** In our three stress-test runs no judge ever rated a finding above its highest reviewer, because brief version 2 gave it no way to: one finding, silent data loss, ended LOW, MED or HIGH depending only on whether one reviewer happened to rate it high. In version 3 the judge sets each severity itself and gives one of five rulings: REAL, PARTLY REAL (part of the claim doesn't hold, same severity), OVERSTATED (lower), UNDERSTATED (higher) or NOT REAL, each compared with the highest severity a reviewer gave, with each reviewer's severity, its own and a one-line reason for every change. The appeal then checks every severity the judge changed and every finding it left at LOW, as well as its dismissals, and Claude logs each verdict, so how often it disagrees on unchanged LOW findings, the part that costs most, can be judged later. Brief version 2 stays selectable with `--brief-version 2`, and its runs are compared apart from version 3's.
- **Kept means checked, and over-rated problems still count.** The comparison's main share is the findings kept after checking, REAL or OVERSTATED: an OVERSTATED finding is a real problem rated too high, so a judge that is strict on severity doesn't make a council look as if it found less. How often the judge cut a kept finding's severity is shown separately, as severity calibration. Without a judge, Claude checks each finding before counting it, or records the run as unverified, and unverified runs are left out of the kept and dismissed shares.
- **Fixes are followed up.** Fixes that fail their recheck, and new problems they cause, are part of a council's cost, so the log keeps them.

## How it compares

- **Anthropic's code-review plugin and `/code-review`** (including ultra) review a pull request with several agents in a fixed setup. Council Dial is for comparing council setups: you choose the type, and every run's type and results go in a log you can compare.
- **Fixed review councils** such as claude-code-review-council (yeameen), agent-review-panel (wan-huiyan), review-council (deployhq), pantheon (the-cybersapien) and council-review skills run one council design, some with other vendors' models. Council Dial runs only Claude subagents, lets you choose among specialised or generalist reviewers, judged, pooled or consensus combining, debate, sequential and baseline, and keeps the briefs fixed so runs compare fairly.
- **council-review-skill** (this-Demir) has five fixed specialists (security, readability, QA, performance, architecture) review at once and cross-reference each other, with security claims taken from real scanners. Council Dial lets you choose the reviewers and how their findings are combined, and logs each setup's results.
- **devils-council** (astrowicked), mainly for OpenCode with Claude Code as a second runtime, has fixed personas (staff engineer, SRE, product manager, devil's advocate, plus ones that join on signals) critique plans, PRs and RFCs, with a chair that sets out their disagreements. Council Dial checks and counts findings so different council setups can be compared.
- **rcl** (allocator-one) is a command-line tool that sends a change to several vendors' models in different roles, through their API keys, and merges their findings into one consensus report that marks which ones block. Council Dial runs only Claude subagents in Claude Code and records which setup ran and what it found.
- **claude-code-expert** (TheLobbi) has a `/cc-council` command that runs a review with a deliberation protocol (such as expert panel, blackboard, red-blue team or Delphi) and preset you pick for the change. Council Dial also lets you choose the setup, and logs every run's setup and results so you can measure which works best on your own material.
- **council-review** in maggy (alinaqi), a larger Claude Code setup kit, validates plans, architecture changes and PRs with a multi-model panel set up in `~/.claude/council.yaml`, approving them when enough reviewers agree. Council Dial runs only Claude subagents and is for comparing council setups, not approving work.
- **super-review-council-claude** (molang163) is a Claude-only review, fix and re-review loop that tests every finding against the code before it counts and keeps fixing until the target is clean. Council Dial's reviewers change nothing, and Claude fixes things only if you ask after the council; Council Dial records whether those fixes held up on recheck.
- **review-council** (WiktorStarczewski) sends a change to reviewers from different labs (OpenAI and Anthropic, plus Gemini when it's installed), checks each claim at the line it cites, fixes what holds up and sends the fixes back for review. Council Dial uses only Claude subagents, fixes only when you ask after the council, and is for comparing council setups over time.
- **reviewteam** (jcr211) keeps a findings ledger and calibrates each critic. Council Dial compares whole council types, including whether their fixes held up on recheck.
- **Debate and decision councils** such as claude-council (amgadelgamal), council (tsenart), debate (strml), claude-consensus, configurable-council (shinytoyrobots), war-room and advisory councils weigh opinions or decisions. Council Dial is for reviews, with findings checked and counted.

## Limits

- The counts come from Claude's reading of the reports, and "kept" is only as good as the judge or Claude's own check.
- Comparisons need many runs on similar material; a handful of runs says little, and Claude says so.
- The kept share isn't comparable across combine methods. Combined findings mean different things for each: a judged run counts the judge's merged list, including what it dismissed; a pooled run counts every finding; a consensus run counts only findings a majority raised, so it filters before counting and scores higher by construction. Compare types within one combine method, or, to compare across methods, score each run against an answer key where one exists, such as the sample's: planted bugs caught and false alarms.
- The baseline's findings are counted confirmed or not, with no OVERSTATED bucket: a real baseline finding counts as confirmed even if its severity was too high, so "council kept vs baseline confirmed" compares like with like, but the baseline's severity calibration isn't recorded.
- Wall time depends on load as well as the type, and the critical path depends on the durations Claude Code reports; the two are kept apart, but a type may have one and not the other (see [Models, tokens and time](#models-tokens-and-time)).
- Token figures are context sizes, not billed totals (see [Models, tokens and time](#models-tokens-and-time)), so they compare runs but don't give their cost.
- The token estimate is the average of earlier runs of the same type, whatever material they reviewed: Council Dial doesn't record the material's size, so it can't scale the estimate to it.
- The same model can appear under two type names: `@opus` when a run asked for the alias, and `@claude-opus-5-5` when the subagents inherited the session's model. Such runs are compared, and estimated, apart.
- On Bedrock or Vertex, the main session's model id isn't recorded, because the script accepts only ids of the form `claude-…`. A run there whose subagents inherit the session's model has no model in its type's name, so it is compared, and estimated, together with other runs whose model wasn't recorded, whatever model they ran on.
- Finding numbers (a reviewer's 1, 2, 3, the judge's M1, M2) restart in every run, so Council Dial cites them with the run id, such as `20261107-2f23/M12`.
- Debate is one round, and sequential runs take longer by design.
- Subagents can fail or stop early; the run is logged with what came back.
- If two runs write the log at the same moment, `review-log.md` can miss the other's row until the next write (the `.jsonl` log keeps both).
- A run with a baseline is grouped with runs of the same council type without one; the baseline doesn't change the council. Brief versions 1 and 2 aren't separated in the comparison: version 2 (Council Dial 1.1.0) added the appeal, which shows in the type's name, and changed how the judge counts the severity of NOT REAL findings and asked it for reasons, which doesn't. Version 3 types end in ` v3`, so they're always compared apart.
- In brief version 2 the appeal checks only findings the judge marked NOT REAL, not ones it marked OVERSTATED. In version 3 it also checks every severity the judge changed and every finding it left at LOW, but not findings left unchanged at MED or HIGH. There is one appeal agent, and its view is advice, so the judge's counts stay as they were and your calls are logged next to them.
- Runs logged before Council Dial 1.2.0 have no model recorded, so their type names don't end in a model and they're compared apart from later runs of the same type.
- The check for a primed description looks for words such as "planted", "on purpose" or "known issues"; a description that hints at problems in other words gets through.
- Recheck results add up per run and can't be corrected, only added to; `newFindings` is recorded but not compared.
- A review log that came with a project you cloned is read like your own; lines that don't pass the script's checks are skipped and counted. Rows written by hand or by an older version are read with their values checked but not whether they add up, so impossible counts in such a row can skew the shares.
- A run logged with `verified` left out, whose confirmed, overstated and dismissed counts are filled in but don't add up to the combined findings, still counts as verified.
- Custom roles are compared without regard to their order or capitals, including for sequential councils, where the order of reviewers does change the run; role names appear in lower case in the type.
- Email addresses and some bare web addresses in a target may still show as links in `review-log.md` on GitHub.

## Planned (not built yet)

None of this is in Council Dial yet, and whether it's built depends on what the research finds.

- **Task templates in plain words.** You'd describe the job, such as "review my creative app" or "legal review of these terms", and Council Dial would pick a ready-made council template for it: the type, the roles and which model each seat uses. It would then tell you which template it used. Templates would start as best guesses and be updated from logged results, as the review log shows which councils find the most for the effort on each kind of task. Council Dial would stay offline: templates would ship with the plugin, and any online lookup of newer templates would be a separate, optional add-on you choose to install; Council Dial itself would still make no network requests.
- **A fingerprint of the material.** Each plan would record which version of the material was reviewed (a git commit, or a content hash of the target files), and `compare` would warn when runs of the same type reviewed different versions, since today it can't tell.
- **An appeal for dangerous commands.** When you allow running code, a separate agent could check each command a reviewer wants to run before it runs.

## Troubleshooting

- **"no planned run":** the run id is wrong, or the log is in another folder; run `list`, or pass the same `--log-dir` as when it was planned.
- **"findingsPerReviewer has N numbers":** give one number per reviewer in the plan's order.
- **"has no results logged yet":** log the run's results before adding a recheck.
- **"--main-model is the main session's model id":** the script takes only an id as Claude Code names it on Anthropic's API, starting `claude-` (such as `claude-opus-5-5`, or `claude-opus-4-6[1m]` for an older model's 1M-context version). A Bedrock id (such as `us.anthropic.claude-opus-5-5-v1:0`) or a Vertex id (such as `claude-opus-5-5@20261001`) isn't accepted, so Claude leaves `--main-model` out, plans the run without recording the main model, and tells you so.
- **"unexpected EOF while looking for matching" or a garbled report:** the text was put in the command with a heredoc or quotes. Write it to a file and pass `--input <file>`, which SKILL.md makes the standard way.
- **"the report has &lt;, &gt; or &amp; and no < or >":** the report came from a completion notice that escaped those characters; save it again with `--notice-escaped --replace`.
- **"node" isn't found:** install Node.js 18 or later.
